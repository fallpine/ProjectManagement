# 通用 AI App 开发流程

本指南面向使用 AI 辅助开发 App 的个人开发者，覆盖从想法到第一版可用产品的完整过程，不限定技术栈。部署和商店上架属于按需执行的交付分支。

## 流程概览与使用说明

**明确需求与范围 → 确认页面与交互 → 确认视觉设计 → 整理 PRD → 制定技术方案与开发计划 → 分阶段开发与验证 → 整体验收与交付**

| 阶段 | 要回答的核心问题 | 主要产出 |
| --- | --- | --- |
| 1. 需求与范围 | 给谁用、解决什么、第一版做到哪里？ | 需求清单、范围边界、待确认问题 |
| 2. 页面与交互 | 用户如何完成主要任务？ | 页面清单、导航关系、操作流程 |
| 3. 视觉设计 | 页面呈现什么效果，如何保持一致？ | 关键页面参考、视觉规范 |
| 4. PRD | 已确认要做什么，怎样算完成？ | PRD.md |
| 5. 技术方案与计划 | 用什么实现，先做什么，如何验证？ | 技术方案、分阶段开发计划 |
| 6. 开发与验证 | 当前阶段是否形成可用闭环？ | 可运行版本、进度和验证记录 |
| 7. 验收与交付 | 第一版是否满足要求，如何使用和接手？ | 验收记录、运行说明、已知问题 |

使用时注意：

- 将提示词中的 `［填写项］` 替换为真实信息；不知道的内容明确写“待确认”，不要让 AI 当作已确定事实。
- 每个阶段先检查输入，再开展工作；达到确认标准后进入下一阶段。已有项目可以复用现有文档、设计和代码，但要先核实是否符合当前需求。
- PRD 可以从草稿开始，随讨论逐步完善。开发以已确认内容为依据，关键待确认事项解决后才实施依赖它的功能。
- 出现范围变化时，先记录变更并确认，再同步 PRD、验收标准和开发计划，最后修改代码。
- 按完整功能闭环拆分开发：页面、交互、数据与验证共同完成，避免所有页面都做了却没有可用功能。
- 文中建议的文档名称用于组织交付物，可与项目已有文档合并，不必为每个阶段创建独立文件。

## 可视化需求与开发进度

配套说明见 [使用说明](使用说明.md)，初始化文件位于 [进度看板模板](进度看板模板)。将整个 `项目管理` 目录复制到 App 项目后，AI 维护 `项目管理/进度看板/项目进度.json`，运行标准库 Python 生成器，用户直接打开 `项目管理/进度看板/开发进度看板.html` 查看。HTML 是只读快照，每次更新数据后必须重新生成并刷新。

- **需求关联**：PRD 使用稳定需求编号，任务关联对应需求与验收标准；按完整功能闭环拆分，记录阶段、范围、依赖和必要验证方式。
- **状态口径**：任务为“未开始／进行中／已完成”；已实现但必要验收未通过仍为“进行中”，附待验证标记。阻塞单独记录，不能凭代码存在或构建通过判定完成。
- **统计口径**：只有未取消且关联需求均已确认、未取消的任务计入完成率；草稿和取消历史单独展示。无有效任务显示“暂无任务”，筛选不改变整体统计。
- **变更同步**：先记录草稿并确认，再同步 PRD、开发计划与 JSON。新增任务分配新编号；取消保留历史；返工只重新打开受影响任务，保留原完成记录和验收依据，其他任务维持状态。
- **文档职责**：JSON 是看板与任务状态的唯一数据来源。主 PRD／迭代 PRD 保留需求依据和关联编号；已有进度文档继续承载交接与详细验证说明，引用任务编号，避免重复维护状态表。
- **生成保障**：生成前校验重复编号、无效关联、缺失依赖、依赖循环和完成依据；失败时保留旧 HTML。生成器不判断证据真实性，AI 必须记录实际结果。

每轮开发、验收、变更确认及对话交接后，按实际路径执行：

```sh
python3 项目管理/tools/generate_board.py
```

模板默认没有真实需求和进度；`演示` 子目录仅用于说明界面与变更行为。完整字段与维护方式见配套使用说明。

## 1. 明确需求与范围

**目标：** 把产品想法变成边界清楚、可以讨论和验收的第一版需求。

**输入：** 产品想法、目标用户、典型使用场景、运行平台，以及已有参考资料。

**使用者需要做：** 说明核心问题和最重要的功能，提供时间、预算、设备、联网、隐私或数据保存等实际约束，并回答关键问题。

**AI 需要做：** 检查信息缺口，区分产品目标与实现方式；对关键选择给出选项和理由，整理必须完成、暂不实现及待确认内容，不擅自扩展功能。

**交付物：** 产品目标、需求清单、第一版范围、约束条件、待确认问题。

**进入下一阶段的条件：** 目标用户、核心场景、平台和第一版边界已经确认；影响整体流程的关键问题已经解决。

### 可复制提示词

```text
我想开发一个［产品描述］，面向［目标用户］，解决［核心问题］。
典型使用场景是［场景］，运行平台是［平台］。
第一版希望包含［核心功能］，暂不包含［排除项］。
已有条件和限制是［现有项目、时间、预算、联网、数据保存等；未知项写待确认］。

先不要写代码或创建项目。请先阅读我提供的资料，检查需求缺口。
无法从资料确认的关键问题，每次问一个，提供有意义的选项并说明推荐理由。
确认后，用普通语言整理产品目标、第一版必须完成的功能、暂不做的内容、约束和待确认项。
请为核心场景提出可检查的完成标准，等待我确认范围。
```

## 2. 确认页面与交互

**目标：** 明确用户从哪里进入、如何操作、操作后发生什么，形成完整使用流程。

**输入：** 已确认的需求范围、核心场景及已有页面参考。

**使用者需要做：** 确认功能入口、导航方式、操作习惯和流程是否符合预期。

**AI 需要做：** 梳理页面层级、导航关系、页面内容、主要操作和结果；补齐必要的加载、空数据、失败、取消及返回状态。涉及删除等不可恢复操作时明确确认方式。

**交付物：** 页面清单、导航关系、核心操作流程、页面状态说明；必要时提供线框图。

**进入下一阶段的条件：** 用户可以按描述完整走通核心场景，页面职责明确，关键操作与数据变化没有歧义。

### 可复制提示词

```text
根据已确认的［需求文档或需求内容］，梳理页面与交互，先不要编码。
请说明页面结构、导航关系、每个页面的内容、主要操作及操作结果。
围绕［核心使用场景］描述从进入到完成的完整流程，并补充必要的加载、空数据、失败、取消和返回状态。
涉及数据修改或删除时，说明何时保存、何时放弃，以及是否需要二次确认。
必要时提供简单线框图。发现需求缺口先提问，不自行新增功能。
输出页面清单和交互说明，等待我确认。
```

## 3. 确认视觉设计

**目标：** 先确认关键页面效果，再建立可复用的视觉规范。

**输入：** 已确认的页面与交互、品牌资料、参考截图或已有组件规范。

**使用者需要做：** 选择视觉方向，提供偏好或参考，确认关键页面效果。

**AI 需要做：** 优先复用现有设计；缺少设计方向时提供少量可比较方案。围绕核心流程给出关键页面参考，归纳颜色、字体、间距和组件状态，考虑不同屏幕、长文本和必要的无障碍要求。

**交付物：** 关键页面设计参考、视觉规范、素材及占位内容清单。

**进入下一阶段的条件：** 关键页面效果已确认，其他页面可以沿用同一套规范，待替换素材有明确记录。

### 可复制提示词

```text
根据［已确认的页面与交互资料］，整理视觉设计方案。
参考资料是［截图、品牌或现有设计规范；没有则写无］，设计偏好是［偏好或待讨论］。
优先复用项目已有组件和规范；没有既定方向时，先给出少量可比较方案，说明适用理由。
方向确认后，先提供［关键页面］的设计参考，再总结颜色、字体、间距和组件状态规范。
明确标注占位内容与待补充素材，不将参考图中的额外功能加入需求。
本阶段只确认设计，不开始业务代码开发。
```

## 4. 整理 PRD

**目标：** 将已确认内容整理为统一开发依据，并建立可执行的验收标准。

**输入：** 已确认的需求、页面与交互、视觉设计及决策记录。

**使用者需要做：** 审阅 PRD，确认功能边界、数据要求和验收标准，解决阻塞开发的关键待确认项。

**AI 需要做：** 汇总确认结果，检查冲突、遗漏及不可验证的表述。为需求设置简短编号，方便开发任务与验收结果引用。

**交付物：** `PRD.md`，至少包含：

- 产品目标、目标用户和使用场景。
- 第一版必须完成的功能、暂不实现的功能和约束。
- 页面框架、导航关系、首页内容及各模块职责。
- 核心交互、模块之间的关系和必要的页面状态。
- 数据内容、必要操作、保存要求；适用时说明备份和恢复需求。
- 视觉设计依据及素材状态。
- 按需求编号组织的验收标准、待确认项和变更记录。

**进入下一阶段的条件：** PRD 已确认，无影响技术方案的关键矛盾或缺项；每项必须完成的功能都有可检查标准。

### 可复制提示词

```text
请将［需求、页面交互、设计及决策资料］中已经确认的内容整理并保存为 PRD.md。
包含产品目标、用户场景、第一版范围、页面导航、模块职责与关系、交互、数据要求、设计依据和验收标准。
给需求设置简短且稳定的编号，便于后续开发任务和验收记录引用。
同步项目管理/进度看板/项目进度.json 中的需求范围、确认状态和验收标准；未确认需求保留草稿，不计入正式进度。
验收标准应说明使用条件、操作和预期结果，避免仅写“正常”“流畅”等无法判断的表述。
未确认内容单独列出；发现冲突先指出，不自行选择或补充功能。
保留明确的第一版排除项和变更记录，供我审阅确认。
```

## 5. 制定技术方案与开发计划

**目标：** 确定实现路径，并拆成有依赖顺序、可运行、可验证的开发阶段。

**输入：** 已确认的 PRD、现有项目代码与规范、设计资料、开发环境信息。

**使用者需要做：** 确认影响成本、维护或产品能力的关键技术选择，提供无法从环境获取的必要约束。

**AI 需要做：** 先检查项目现状，优先复用现有实现；确定技术栈、模块职责、数据保存方式及必要接口。识别外部服务、权限、设备和依赖风险，将核心功能闭环排在前面。

**交付物：** 保存在 `项目管理/进度看板/开发计划/` 中的技术方案和分阶段开发计划。每个阶段至少写明目标、关联需求编号、前置依赖、实现范围、交付物及验证方式。

**进入下一阶段的条件：** 关键技术决策已确认，每阶段具备可执行任务和验收依据，阻塞项有明确处理方式。

### 可复制提示词

```text
根据［PRD.md 路径］和［项目路径或新项目说明］，制定技术方案与开发计划，先不要编码。
先阅读项目规范、检查现有代码和环境，区分已有能力与需要新增的内容。
明确技术栈、模块划分、数据保存方式和必要接口；存在影响成本或维护的重要取舍时，给出选项并向我确认。
按依赖关系拆分开发阶段，优先实现一个完整核心功能闭环，再扩展其他功能。
每阶段写明目标、关联需求编号、前置依赖、实现范围、交付物和验证方式。
列出外部依赖和阻塞项，避免超出 PRD 的功能及不必要的抽象。
保存已确认的技术方案和开发计划，作为后续实施依据。
在项目管理/进度看板/项目进度.json 中按功能闭环拆分任务，关联需求编号，记录阶段、范围、依赖、验收标准和必要验证类别。
已有任务核对实际实现及验证后更新，不重复创建、不将历史完成项无依据重置；更新后生成看板。
```

## 6. 分阶段开发与验证

**目标：** 按计划持续交付可用功能，并留下真实、可追溯的验证记录。

**输入：** 已确认的 PRD、设计、技术方案、开发计划及项目规范。

**使用者需要做：** 回答实施中出现的关键产品问题，完成约定的人工或设备验证，并反馈实际结果。

**AI 需要做：** 按阶段实施最小必要修改，保持现有风格，保护无关改动；完成适用检查，修复本次问题并同步进度。出现需求变化时先确认并更新文档，再执行相关修改。

**交付物：** 可运行代码，以及保存在 `项目管理/进度看板/开发进度/` 中的阶段进度记录、验证结果、剩余事项和已知问题。

**进入下一阶段的条件：** 当前阶段通过对应检查；未验证项明确标注，依赖该结果的后续工作不得直接视为已通过。

### 验证结果应分别记录

| 验证类别 | 能说明什么 | 不能替代什么 |
| --- | --- | --- |
| 编译或构建 | 当前环境下可以编译、打包 | 完整运行行为和交互正确性 |
| 静态检查 | 类型、语法和部分代码问题 | 运行时行为及真实体验 |
| 自动化测试 | 所覆盖场景符合预期 | 未覆盖场景和设备体验 |
| 人工操作 | 指定环境中的流程和显示效果 | 所有平台、设备及边界情况 |
| 真机验证 | 实际设备上的权限、硬件及系统交互 | 其他设备或系统版本上的表现 |

按风险和功能选择必要验证，不为每次低影响修改机械新增测试；已有相关测试仍应按需运行。不要通过删除有效测试、跳过失败检查或降低验收标准制造“通过”。环境不具备时记录原因和待验证项，不编造结果。不得自行运行模拟器；真机操作按使用者明确安排进行。

### 可复制提示词

```text
根据［已确认的开发计划路径］开始实施，并遵守［项目规范路径］。
按阶段完成完整功能闭环，复用已有实现，只修改必要内容，保留无关改动和被注释的代码。
每阶段完成后执行适用的编译、静态检查及相关测试；按风险决定是否需要新增测试，不主动增加测试钩子。
发现失败先定位并修复，不删除有效测试、跳过失败检查或降低验收标准来制造通过。
分别记录实现进度、实际验证结果、待人工或设备验证项及剩余问题，并同步项目管理/进度看板/项目进度.json。
只有已实现且必要验收通过才标记已完成；已实现待验证仍为进行中，阻塞单独记录。每阶段更新实际更新时间并重新生成看板。
不要自行运行模拟器，真机操作按我的明确安排进行。
在已确认范围内持续执行；关键决策或范围变化先向我确认，同步 PRD 和计划后再实施。
遇到阻塞时说明原因，并继续不依赖该阻塞的工作。不要擅自部署、发布或扩展功能。
```

## 7. 整体验收与交付

**目标：** 确认第一版满足已确认需求，并让使用者能够运行、检查和继续维护。

**输入：** PRD、当前版本、开发计划、阶段验证记录及已知问题。

**使用者需要做：** 验收核心使用场景，完成已约定的人工与设备检查，确认交付结果；如需发布，明确发布目标与授权范围。

**AI 需要做：** 按需求编号逐项核对实现和验证状态，检查完整流程、数据保存与异常处理，修复范围内问题。整理运行说明、配置要求、交付资料和已知限制。

**交付物：** 验收记录、运行或构建说明、交付清单、已知问题与后续事项。

**完成条件：** 第一版必须完成的需求均通过对应验收，关键待验证项已完成；如有未通过项，应如实标注未完成，不能宣称全部交付完成。

需要部署或上架时，在此基础上准备对应平台的发布配置、素材和必要文档，并核对当时适用的官方要求。准备资料与实际发布分开记录，实际部署或发布仅在用户明确授权范围内执行。

### 可复制提示词

```text
请对照［PRD.md 路径］验收［当前版本或项目路径］。
按需求编号列出实现情况、验证方法、实际结果和未完成事项，并检查核心完整流程、数据可靠性及必要异常场景。
清楚区分“已实现”“已验证”“待人工或设备验证”“未完成”，不要用编译或静态检查通过代替功能验收。
修复已确认范围内的问题，完成适用的回归检查，并整理运行方式、配置要求、交付清单和已知限制。
按需求和任务编号同步项目管理/进度看板/项目进度.json 的实际验证与验收依据，待验证或未通过项不能计为已完成；重新生成看板。
发布需求是［无需发布／仅准备发布资料／已明确授权的发布范围］。
没有明确部署或发布授权时，只整理所需资料和剩余步骤，不实际发布。
```

## 二次迭代开发流程

适用于已有可运行版本后的功能新增、行为调整、问题修复及较大改版。以现有版本为基础，只梳理本次变化，复用已有设计、架构和文档，不必每次重新执行全部七个阶段。

**输入：** 本次需求、当前版本、项目规范、PRD、开发计划与进度记录，以及相关代码和已有验证结果。

**使用者需要做：** 说明本次目标、优先级及需要保持的行为，确认重要取舍，并完成约定的人工或设备验收。

**AI 需要做：** 先核对现状，再分析变化及影响范围；按改动规模制定计划、精准修改，验证新增行为并回归受影响的现有功能。

### 按改动大小选择流程

| 改动类型 | 推荐流程 |
| --- | --- |
| 文案、颜色、间距等小调整 | 明确位置与预期 → 修改 → 针对性验证；影响需求或设计依据时同步相关文档 |
| 已有功能调整或问题修复 | 核对当前行为或复现问题 → 确认变化及影响范围 → 更新相关文档和计划 → 开发 → 回归验收 |
| 新增模块或较大改版 | 按前文七个阶段执行，但只补充本次变化，复用已经确认的内容 |

是否简化应看实际影响，不只看代码量。涉及共享组件、数据结构、权限或外部接口时，即使修改较少，也要检查相关流程。

### 新需求如何维护 PRD

默认采用“主 PRD 持续更新，大迭代按需新增独立文档”。不必每次出现新需求都新建 PRD。

| 情况 | 推荐做法 |
| --- | --- |
| 小功能、已有功能调整 | 直接更新主 `PRD.md`，补充需求、验收标准和变更记录，标明实现状态 |
| 新增较独立的模块、较大版本迭代，或多个版本同时推进 | 按需新建迭代 PRD，例如 `PRD-v1.1.md`，描述本次变化，并在主 PRD 中关联 |
| 新需求尚未确认 | 先放入需求草稿或迭代 PRD，标记“待确认”，不覆盖已确认需求 |
| 完全独立的新产品 | 为新产品单独建立 PRD，不混入现有产品的迭代文档 |

两类文档的职责：

- **主 PRD**：描述产品完整需求，区分已实现与待开发内容；采用独立迭代文档时，关联对应需求和状态。
- **迭代 PRD**：记录本次相对已有版本新增、修改、删除的内容，以及影响范围、验收标准和关联的主 PRD 需求编号，避免复制整份主文档。

使用独立迭代 PRD 时，按以下顺序维护：

1. **讨论需求**：新建迭代 PRD，注明对应的现有版本、目标版本或迭代名称，整理本次变化；未确定事项标记为待确认。
2. **确认范围**：需求确认后，在主 PRD 中添加本次迭代的摘要、关联链接和待开发状态，保留当前已实现行为的说明。
3. **开发实施**：本次变化以已确认的迭代 PRD 为依据，未涉及内容沿用主 PRD。需求变更先确认，再同步迭代 PRD、主 PRD 中的相关摘要及开发计划；文档冲突必须澄清，不能自行选择一份执行。
4. **验收整合**：验收通过后，将最终需求整合到主 PRD 并更新实现状态；未完成或待验证内容继续如实标注，不提前标记完成。
5. **保留历史**：将迭代 PRD 标记为已验收的历史记录，保留最终范围和验收结论。后续工作以更新后的主 PRD 及新的已确认迭代为依据。

对于个人开发，优先直接维护主 PRD；仅在拆分能帮助管理需求时新增迭代文档。

### 迭代步骤与交付物

| 步骤 | 工作内容 | 交付物或完成条件 |
| --- | --- | --- |
| 1. 核对现状与变化 | 阅读文档及相关实现，说明当前行为、本次新增／修改／删除内容、必须保持的行为；问题修复需记录复现条件 | 本次范围和验收目标确认；文档与代码冲突已澄清 |
| 2. 分析页面与设计影响 | 检查受影响页面、入口、返回路径及关联操作；沿用现有视觉规范，无视觉变化时跳过设计环节 | 必要的交互与设计变化已确认 |
| 3. 更新需求依据 | 按上述规则更新主 PRD 或新增迭代 PRD，明确本次需求、验收标准和变更记录 | 文档职责与实施依据清楚，本次变更可追溯 |
| 4. 制定迭代计划 | 分析模块依赖、共享能力、接口和已有数据的影响，按依赖关系拆分任务 | 每项任务具备范围、关联需求和验证方式 |
| 5. 实施与回归 | 精准修改，验证本次目标及受影响的旧功能，修复本次引入的问题 | 实现结果和实际验证记录齐全，待验证事项明确 |
| 6. 验收与交付 | 对照本次标准验收，将已验收需求整合到主 PRD，更新开发进度和变更说明；按项目约定记录版本信息 | 本次必须完成的需求通过验收，相关旧功能无已知回归 |

涉及已有用户数据时，在实施前明确旧数据的读取、默认值和保存行为；确需迁移时，确认迁移触发方式、失败处理及数据保护措施。按实际风险验证旧版本数据升级和新数据使用，不为无关改动额外设计迁移机制。

验证方式沿用前文约定：区分编译、静态检查、自动化测试、人工操作和真机验证；不自行运行模拟器，不将待验证事项写成已通过。部署或发布仍只在用户明确授权范围内执行。

### 开始迭代的提示词

```text
本次是在现有 App 上进行迭代，需求是［具体变化或待修复问题］。
需要保持的现有行为是［约束；没有额外要求可省略］。

先阅读项目规范、PRD、开发计划和进度记录，检查相关代码。
梳理当前行为、本次变化、影响范围和验收标准；问题修复先核对复现条件。
优先复用现有设计和实现，不重新设计无关模块，不重做已完成的功能。
如果涉及已有用户数据、共享组件或外部接口，说明兼容要求和必要的回归范围。

先不要修改代码。对无法从项目中确认的关键事项向我提问，确认后给出与改动规模匹配的迭代计划。
计划中说明直接更新主 PRD 还是新增迭代 PRD，明确文档关联、实施任务及验证方式。
读取项目管理/进度看板/项目进度.json，识别受影响的需求与任务；变更草稿记录新增、修改、取消内容及统计影响，确认前不覆盖正式范围。
未确认需求先保留为草稿，不覆盖已确认内容。
```

### 确认计划后开始实施的提示词

```text
按刚才确认的迭代计划实施，按约定更新主 PRD 或迭代 PRD，并同步开发计划。
如使用独立迭代 PRD，本次变化以其已确认内容为依据，未涉及内容沿用主 PRD；发现冲突先澄清。
只修改本次范围内的内容，保留无关改动，保持现有风格。
验证本次需求，并回归受影响的已有功能；涉及旧数据时执行计划中的兼容检查。
遵守项目既有的测试及设备操作约定，不擅自部署或发布。
完成后同步项目管理/进度看板/项目进度.json 和变更说明，列出实际验证结果、待验证事项及已知问题。
取消项保留历史；已完成任务需返工时保留原验收记录及重新打开原因，仅调整受影响任务。
已实现且必要验收通过才计为完成，更新实际更新时间并重新生成看板。
验收通过后，将最终需求整合到主 PRD，更新实现状态，并保留迭代 PRD 作为历史记录。
```

### 本次迭代验收清单

- [ ] 本次新增、修改、删除的内容及必须保持的行为已经确认。
- [ ] 主 PRD 与迭代 PRD（如有）的关联和实施依据明确，计划、实现状态及验收结果可以对应。
- [ ] 已验收需求已整合到主 PRD；独立迭代 PRD 已标记状态并保留，未完成内容未标记为完成。
- [ ] 本次功能或问题修复通过验证，受影响的旧功能已完成必要回归。
- [ ] 涉及已有数据时，兼容或迁移行为已按计划验证。
- [ ] 未验证项和遗留问题如实记录，未扩大修改范围或覆盖无关工作。
- [ ] 开发进度与变更说明已更新，可以使用后文交接模板继续下一轮工作。

## 阶段完成检查清单

- [ ] 需求：目标用户、核心问题、平台、第一版范围及排除项已经确认。
- [ ] 交互：页面职责、导航、主要操作和必要异常状态已经确认。
- [ ] 设计：关键页面效果、复用规范及待替换素材已经记录。
- [ ] PRD：需求有编号，必须完成的功能有验收标准，关键待确认项已解决。
- [ ] 计划：技术方案已确认，每阶段都有依赖、范围、交付物和验证方式。
- [ ] 开发：阶段进度与实际代码一致，失败已处理，未验证事项没有被标记为通过。
- [ ] 验收：第一版必须完成的需求通过验收，运行说明和已知问题完整。
- [ ] 发布（如适用）：发布准备与实际发布状态分开记录，执行范围符合用户授权。

## 新对话接续工作的上下文交接提示词

在同一个项目中开启新对话时，可以省略重复的项目介绍和路径清单，让 AI 先查阅当前项目文件。为确保接续可靠，不要把“同一个项目”当作已提供上一段对话的全部决策；切换前将重要决定、进度和验证结果写入项目文档。

### 第一步：在旧对话中保存上下文

准备切换对话时，先在旧对话中发送下面的提示词，将本次工作的状态写入项目文件，无需手动整理：

```text
我准备在同一个项目中开启新对话，请先保存本次工作的上下文：

1. 将已确认的需求变化和重要决定同步到 PRD、开发计划等对应文档。
2. 更新项目管理/进度看板/项目进度.json 并重新生成看板；首次使用时按配套模板初始化，核对真实进度，不套用演示数据。沿用已有进度文档记录交接说明；如没有，可在 `项目管理/进度看板/开发进度/` 中创建「开发进度.md」，引用任务编号，不重复维护状态表。
3. 记录当前阶段、已完成内容、实际验证结果、待验证事项、已知问题和建议下一步。
4. 标明需要保留的未提交改动，不要自动提交或覆盖它们。

只记录实际发生和已经确认的内容，未验证的不写成通过。
完成后告诉我更新了哪些文件。
```

等待文件更新完成后，再开启新对话。建议在 `项目管理/进度看板/开发进度/` 中持续维护同一份 `开发进度.md`；如果项目已有进度记录，则沿用现有文件，不重复创建，并在后续提示词中使用其实际名称。

### 第二步：在新对话中接续工作

以下模板适用于新对话能够访问最新项目文件的情况；若使用其他工作树或分支，先确认需要的文档和改动已在当前工作目录中。

进度已经保存时，直接发送：

```text
请阅读项目规范、项目管理/项目需求中的 PRD、项目管理/进度看板/开发计划和开发进度中的 Markdown 文档，以及项目管理/进度看板/项目进度.json，核对代码现状及实际验证后，继续完成［具体任务］。
遵守已确认范围，保留无关修改；有关键疑问先询问，完成后同步 JSON 中的进度和验证结果，并重新生成看板。
```

如果还有尚未写入文档的进度或特殊约束，使用下面的补充模板：

```text
请继续当前项目的开发，先阅读项目规范、项目管理/项目需求中的 PRD、项目管理/进度看板/开发计划和开发进度中的 Markdown 文档，以及项目管理/进度看板/项目进度.json，并核对代码现状及实际验证。

当前进度：［一句话说明；已写入文档可省略］
本次任务：［接下来要完成的内容］
特殊约束：［尚未写入文档的决定或限制；没有可省略］

按已确认的需求和计划继续，不重复已完成工作，不覆盖无关修改。
缺少关键资料或存在冲突时先询问。完成后同步 JSON 并重新生成看板，说明已验证和待验证事项；不要凭聊天摘要或代码存在标记完成。
```
