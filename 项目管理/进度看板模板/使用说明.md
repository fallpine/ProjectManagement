# 项目内开发进度看板

AI 维护 `项目进度.json`，生成脚本将数据嵌入 HTML。双击 `开发进度看板.html` 即可在支持现代 JavaScript 与 dialog 的浏览器中查看；无需服务、网络或第三方 Python 库。HTML 只读，不能写回数据。

## 开始使用

1. 将本目录复制到 App 项目的 `项目管理` 目录。`演示` 和 `tests` 可不复制；保留 `tools` 中的两个文件。
2. 让 AI 阅读项目规范、PRD、开发计划及实际代码，再填写 `项目进度.json`。空模板没有真实任务，不要把演示进度当作项目进度。
3. 在 App 项目根目录执行（Python 3.9 或以上）：

```sh
python3 项目管理/tools/generate_board.py
```

4. 打开 `项目管理/开发进度看板.html`。后续每次更新 JSON，都必须重新运行生成命令，再刷新页面。只编辑 JSON 不会更新已生成的 HTML。

脚本默认路径基于脚本位置，不受运行目录影响。也可指定路径：

```sh
python3 项目管理/tools/generate_board.py --input 项目管理/项目进度.json --output 项目管理/开发进度看板.html
```

查看本模板演示时，打开 `演示/开发进度看板.html`。演示有效任务为 5 个：未开始 1、进行中 3、已完成 1，完成率 20%，阻塞 1、已实现待验证 1；另有待确认及取消任务各 1 个。

## 数据约定

需求编号推荐 `R-001`，任务编号 `T-001`，变更编号 `C-001`。编号创建后稳定保留，不复用取消项编号。所有字段均需提供，空数组用 `[]`，允许为空的说明用 `""`。时间记录推荐带时区的 ISO 8601 格式，例如 `2026-10-15T13:00:00+08:00`，变更按此格式倒序展示。

顶层包含 `schema_version: 1`、`project`、`requirements`、`tasks`、`changes`。

| 对象 | 字段与含义 |
| --- | --- |
| project | `name` 项目名、`current_stage` 当前阶段、`updated_at` 数据实际更新时间、`demo` 是否演示 |
| requirement | `id`、`title`、`scope`、`acceptance_criteria` 非空验收标准数组、`confirmation`（待确认／已确认）、`cancelled` 布尔值 |
| task | `id`、`title`、`stage`、`scope`、`requirement_ids` 非空需求编号数组、`dependencies` 前置任务编号数组、`status`（未开始／进行中／已完成）、`implemented` 布尔值、`cancelled` 布尔值 |
| task 验收 | `acceptance_criteria` 非空任务验收标准数组、`required_checks` 必要验证类别数组、`verification` 实际验证数组、`acceptance_result`（待验证／通过／未通过）、`acceptance_evidence` 验收依据 |
| task 补充 | `blocked_reason` 阻塞原因、`remaining_items` 未完成事项数组、`history` 状态历史数组 |
| verification | `category`（构建／静态检查／自动化测试／人工操作／真机验证）、`result`（待验证／通过／未通过）、`evidence` 实际结果与证据位置、`checked_at` 验证时间；每类只保留当前结果，旧结果在历史或验证文档保留 |
| history | `at`、`status` 当时状态、`note` 变化原因与旧验收结论或记录位置 |
| change | `id`、`type`（新增／修改／取消）、`confirmation`（待确认／已确认）、`at`、`summary` 变化内容、`reason` 原因与统计影响、`requirement_ids`、`task_ids` |

需求的关联任务由 `task.requirement_ids` 反向计算，不另存任务列表，避免双向维护不一致。具体对象示例见演示 JSON。

### 状态与统计

- 只有任务未取消，且它关联的**所有**需求都已确认且未取消时，才是有效任务。跨正式需求和草稿的任务不计入，应优先拆分。
- 完成率 = 已完成有效任务数 / 有效任务数，四舍五入到整数百分比。无有效任务时显示“暂无任务”。筛选仅影响看板，不改变整体统计。
- `implemented: true` 但尚未验收通过的任务为“进行中”，附“已实现 · 待验证”。阻塞数量独立统计，可与待验证重叠。
- “已完成”必须已实现、验收通过且有依据；必要验证全部通过，实际记录不得仍有失败或待验证；阻塞及未完成事项必须清空。仅构建或静态检查通过不等于功能验收。
- 必要验证按风险选择，允许无适用的检查类别，但完成仍必须有真实的验收依据。不要通过清空必要验证类别或删除失败记录制造完成。
- 脚本校验结构与记录一致性，不能判断证据真伪，也不监控源代码。AI 必须如实维护；用户按需完成设备或人工验收。

### 需求变更

1. 新变化先加入 `changes`，设为“待确认”；对于修改或取消既有需求，提议内容写在变更摘要中，**不提前覆盖原需求、任务与验收标准**。全新需求可另建待确认需求及任务。
2. 用户确认后同步主 PRD／迭代 PRD 和开发计划；将对应变更标记为已确认，再同步 JSON。
3. 新增分配新编号；修改仅调整受影响任务。已完成任务需要返工时，先将原完成时间、验收结论及证据位置保存到 `history`，再改为“进行中”，重置已失效的实现／验收／验证结果，补充新验收标准与剩余事项。未受影响的记录保留。
4. 取消使用 `cancelled: true`，需求和关联取消任务都保留，历史不删除；仍服务于其他有效需求的任务应重新核对并调整关联，避免误排除。
5. 更新 `project.updated_at`，运行生成器。说明新增、取消、返工如何影响任务分母或完成数量。

生成器不自动合并 PRD，也不能从一个 JSON 快照判定历史是否被误删。变更追溯靠上述维护规则及项目版本管理；建议将 JSON、生成工具及生成 HTML 一同纳入项目已有版本管理。

## 文档职责与 AI 提示词

PRD 描述产品及验收要求，开发计划描述顺序和依赖；JSON 是任务状态和看板的唯一来源。已有 `开发进度.md` 沿用作交接、问题和验证说明，引用需求／任务编号，不另建重复状态表。文档中的状态摘要如有保留，应从 JSON 同步。

```text
请阅读项目规范、PRD、开发计划、已有进度记录和项目管理/项目进度.json，核对代码与实际验证结果。
按已确认需求编号拆分可交付、可验证的任务，记录范围、依赖、验收标准和必要验证类别。
只同步真实进度，不凭聊天摘要、代码存在、构建或静态检查通过就标记已完成。
未确认需求和变更保留为草稿，不覆盖当前正式范围。
范围变化确认后同步 PRD、计划及 JSON，仅调整受影响任务；取消保留历史，返工保留原完成与验收记录。
完成本轮工作后更新 JSON 的实际更新时间并运行：
python3 项目管理/tools/generate_board.py
如校验失败，修复数据且保留旧看板，不降低验收标准。说明本轮更新、实际验证、待验证事项及阻塞。
```

## 检查

```sh
python3 -m unittest discover -s 进度看板模板/tests -v
```

如已安装 Node.js 18 或以上，可额外运行页面脚本单元测试（生成和使用看板不需要 Node.js）：

```sh
node 进度看板模板/tests/test_board.cjs
```

复制或改名后将命令中的目录替换为实际路径。页面脚本测试使用最小 DOM 替身，不启动浏览器。Python 测试涵盖结构、完成门槛、依赖、文本转义和失败时保留旧页面。页面布局、点击、键盘与真实浏览器离线体验需另行检查，自动化数据检查不替代视觉验收。
